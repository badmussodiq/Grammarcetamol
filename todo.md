Object storage is a pluggable `StorageProvider` abstraction (mirrors `PaymentProvider`) — MinIO and real S3 can coexist at once, since every `upload_files` row permanently records which provider/bucket/key it's actually on rather than a resolved URL; switching the "current" provider only affects brand-new uploads, never breaking or migrating existing ones. `S3CompatibleStorageProvider` (via `@aws-sdk/client-s3`) is one class registered twice under different config, since MinIO and AWS S3 both speak the S3 API. Required provisioning MinIO first (`docker-compose.dev.yml`, restart:always on everything, found and left alone an unrelated pre-existing standalone `platform-mongo` container with real `notifications` data). Live-verified with a from-scratch e2e script (no prior e2e harness existed in the repo) against the real stack: real gateway JWT auth, real course-service lookup, a real 2-part multipart upload actually PUT to a real running MinIO instance, and an independent MinIO-side `HeadObjectCommand` check confirming the object exists at the correct size. All 4 spec'd RabbitMQ events confirmed publishing with correct payloads. Admin upload UI itself not built — backend-first, matching every other phase's ordering; Media Service (Task 17) remains deferred pending MongoDB.
